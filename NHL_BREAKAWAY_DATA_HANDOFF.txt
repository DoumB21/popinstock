VERIFIED QUERY FORMULAS (each cross-checked today against a real fan site and/or the
official nhlbreakaway.com site, not just theoretical)
- Per-moment holder list/count: cards WHERE moment_uuid = X AND burned = 0, excluding
  system_wallets.
- Per-set stats (Hoardio's Sets page was built and verified against this, 2026-08-26):
  Moments = collections.template_count (stored)
  Editions = collections.total_supply (stored) — used ONLY as the % denominator below,
    never as a stand-in for "this many rows exist" (see CORRECTED FORMULA note below)
  Distributed = COUNT(*) FROM cards WHERE burned=0 AND owner NOT a system wallet
  In Packs = COUNT(*) FROM cards WHERE burned=0 AND owner_wallet = the wallet whose
    system_wallets.role = 'pack_escrow' (join, don't hardcode — see system_wallets
    entry above). This used to say "either of the two confirmed ones", which is the
    2026-08-26 bug — the crafting_processing wallet's unburned holdings are a
    different bucket, "Other", not In Packs.
  Other = COUNT(*) FROM cards WHERE burned=0 AND owner_wallet = the wallet whose
    role = 'crafting_processing' AND crafting_turn_in IS NOT 1 — NEW 2026-08-26, was
    previously silently merged into In Packs
  Used for Crafting = COUNT(*) FROM cards WHERE
    (burned=1 AND burned_by_wallet = the 'crafting_processing' wallet)
    OR (burned=0 AND owner_wallet = the 'crafting_processing' wallet AND crafting_turn_in = 1)
    — NEW 2026-08-26, was previously just "Burned". The second half of this OR is
    itself a 2026-08-26 fix: a card gets submitted/locked into crafting
    (crafting_turn_in=true on Sweet's live _tokendata) before the on-chain burn
    executes — confirmed via scripts/sync-crafting-turn-ins.js that 23,028 of the
    43,108 cards then sitting in "Other" were actually already mid-crafting. This is
    the ONLY column that needs a live per-token check (crafting_turn_in isn't in the
    bulk search index) — cards.crafting_turn_in is a stored, synced column, not
    computed live at query time.
  Removed from circulation = COUNT(*) FROM cards WHERE burned=1 AND burned_by_wallet
    = the 'pack_escrow' wallet — NEW 2026-08-26, was previously just "Burned"
  Holders = COUNT(DISTINCT owner_wallet) excluding both system_wallets (unchanged —
    this part was always correct)
  In Packs % = In Packs / Editions.  Holders % = Holders / Editions.
  Same primary/secondary split applies to the Holders page's per-edition status label
  (was previously a blanket "In Packs" for both wallets, unburned) and to any other
  page showing a breakdown of where a moment's editions currently sit.
- "Listed" state — NEW 2026-08-26, not stored in the DB, fetch live per page view (same
  decision already made for price/sale history below — a listing can appear/get
  cancelled independent of our sync cadence). `getOpenListings(momentUuid)` in
  lib/sweetClient.js in the NHL Breakaway project wraps
  GET /catalog/listing/moments?campaign_id=826&scroll=true&limit=100&collapse=false
  &offers=true&sweet_is_seller=false&offer_type=fixed-price&sort=price.asc&uuid={moment_uuid}
  — public, no login needed (unlike the per-owner lock endpoint below). Returns every
  currently-open fixed-price listing for that moment, cheapest first; each hit has
  attributes['edition-number'] (join key to cards.edition_number for that moment),
  sequence_number, and current_offers[0].price_usd/listing_id/status. limit=100 in one
  call is enough — verified real listing counts top out well under that (41 on a busy
  3,000-edition moment) — so no scroll_id pagination needed in practice. On the Holders
  page, a card with an open listing here is still "Held" ownership-wise, just add a
  "Listed — $X" indicator on that row instead of a separate status bucket.
  CORRECTED FORMULA, found 2026-08-26 while building this exact page: do NOT compute
  Distributed/In Packs by subtracting from Editions (e.g. "Distributed = total_supply -
  in_packs_count"). That silently assumes every theoretical edition already exists as
  some row, which breaks for a moment that hasn't been minted on-chain yet — found via
  the "895" set (Alex Ovechkin, Mythic, 1/1: zero cards rows exist for it at all, not
  even burned, so the subtraction-based formula wrongly showed Distributed=1 when the
  true value is 0). Always compute both as direct COUNT(*) over real cards rows, never
  by subtracting from Editions/total_supply.
- Per-pack stats (matches nhlba.com's Packs page exactly):
  Moments = pack_moments.highlights_in_pack (stored)
  Opened = COUNT(*) WHERE burned = 1 (opening a pack burns/consumes it)
  Collected = COUNT(*) WHERE burned = 0 AND owner not a system wallet
  Distributed = Opened + Collected (NOTE: packs mint progressively over time, unlike
  cards where the full total_editions cap is usually already minted — do NOT assume
  Distributed = total_editions - system_wallet_holdings for packs the way it works
  for cards/sets; it's simply every row that currently exists in the packs table)
  % Left = Collected / Distributed
- Burned-per-moment: not a stored column, derive via GROUP BY moment_uuid on
  cards.burned — cheap, was live-tested and correct.

SET_UUID IS NOT A CONTRACT ADDRESS, AND NOT THE SAME AS nhlba.com's "P." COLUMN
collections.set_uuid / moments.set_uuid (a long hex string like
cd2f47fea54500000000000000000000) is a Sweet catalog-side identifier, not an on-chain
contract. A real contract address (series_contracts.contract_address) is a standard
40-hex-char 0x address. nhlba.com's own "P." index column is almost certainly just
their internal database row order, not derived from anything in Sweet's data — spot
checked and it does not match Sweet's own real set_id field. Don't try to replicate it.
set_uuid is still useful as a routing key (URL-safe single value) and for building a
conditional link to nhlbreakaway.com/play/{series_id}/sets/{set_uuid} — but that page
only exists for the ~49/84 sets actually enrolled in the Set Completion Challenge
(collections.in_set_completion_challenge), so check that flag before linking. A real
Polygonscan link needs series_contracts.contract_address + cards.sequence_number (per
specific edition) — set_uuid can't be used for that, and a "set" has no single token to
link to in the first place, so that kind of link belongs on a per-edition row, not here.

CRITICAL GOTCHA
Wallet address string comparisons MUST be case-insensitive. This DB stores addresses
in mixed/checksummed case; other sources (URLs, some APIs) normalize to all-lowercase.
A plain `=` comparison will silently return zero rows instead of erroring if the case
doesn't match — always use LOWER(a) = LOWER(b) or ILIKE for any wallet address lookup
that didn't originate from this project's own pipeline.

PRICE / SALE HISTORY — DELIBERATELY NOT STORED, FETCH LIVE PER PAGE VIEW
Sweet's public API has a per-card transaction history endpoint (already wrapped as
getDistributionHistory() in lib/sweetClient.js in the NHL Breakaway project) that
returns: transaction_type, transaction_datetime, edition, amount, currency,
from_username, to_username, explorer_url — per moment/template, one call. Decision made
this session: call this live when a visitor views a specific card's page, don't store
or poll it in the background. Reasoning: unlike ownership (which barely changes and is
cheap to keep in bulk via Alchemy), a live "current listing price" has zero on-chain
footprint and no bulk-fetch endpoint, so keeping it fresh would mean endless per-card
polling with no natural staleness floor. Live current-listing-price/FMV display is
explicitly out of scope / deferred for now, by the user's own choice.

MINT RANKINGS / "EDITION RATINGS" LEADERBOARD — NEW 2026-08-30, BUILT AND POPULATED
This is the feature the two open questions below used to describe as unresolved/not
built — it now is. A new table, `mint_rankings`, is populated and ready to query; no
schema/query design work is needed on your end, just build the UI + API route(s).

WHAT IT IS
For every collection (a `collections` row, keyed by set_uuid/collection_key) and every
real wallet that owns at least one non-burned edition of EVERY template (moment_uuid)
in that collection, this table has one row per "complete set" that wallet can assemble
— a wallet owning 3+ copies of every template in a collection gets 3 rows (set_number
1/2/3), each independently ranked on that collection's leaderboard (a wallet CAN hold
multiple top ranks of the same collection at once — this was an explicit user decision,
not an oversight). set_number 1 always uses each template's single lowest-owned
edition; set_number 2 uses each template's next-lowest; etc — never the same physical
edition reused across two of a wallet's own complete sets.

  collection_key       TEXT     -- == collections.set_uuid, join the same way the Sets/

  wallet_address        TEXT     -- case-INSENSITIVE, same gotcha as everywhere else —

  owner_username         TEXT    -- denormalized, may be NULL (same caveat as elsewhere:

  total_complete_sets    INTEGER -- how many complete sets this wallet owns of this

  set_size               INTEGER -- minted_template_count for this collection at compute

                                    math
  sum_of_editions        INTEGER -- sum of the edition_number used per template for

  avg_edition             REAL   -- sum_of_editions / set_size

                                    used to be a COUNT(*) of currently-held-by-a-real-

                                    gives for collections.total_supply above).

                                    correctly (see above) — worst case every owned

                                    rating bottom out at set_size/total_assets*100
                                    (small, positive), never negative. If you ever see a
                                    negative or >100 value here, that's a real bug to
                                    report back, not expected behavior.

                                    wallet's every complete set for that collection —

  editions_used             TEXT   -- JSON array (json-encoded string, needs

                                    total_editions}, ...]. Does NOT include player
                                    name/image — join each entry's moment_uuid back to

  computed_at                TEXT

SWEET TRANSACTION HISTORY — NEW 2026-09-02, BUILT, BACKFILLED, SYNCED TO RAFF, HOURLY
This directly resolves open question #1 below (sitewide activity feed) — a bulk-ish
per-series history endpoint was found and the "don't poll/store" reasoning from the
PRICE/SALE HISTORY section above does NOT apply here: this data isn't a live listing
price, it's an immutable historical fact (a transaction that already happened never
changes), so storing and syncing it in full has no staleness/correctness downside the
way live prices would.

WHAT IT IS
Sweet's own per-series transaction history (found via network-inspecting
nhlbreakaway.com's own site — same technique as the existing "Listed" state above),
already wrapped as getDistributionHistory() in lib/sweetClient.js in the NHL Breakaway
project. One row per on-chain transaction: purchase (secondary-market sale, with a real
USD amount), trade, gift, pack_open, promo, and transfer. Backfilled ONCE across all 281
distinct series_id (96 covering all 1,965 card moments via heavy sharing — e.g. all 32
Ice Nation player templates share one series_id — plus 185-and-growing 1:1 for pack
templates), 754,429 rows total as of the backfill. Kept current from here on by a new
hourly phase, `sync-sweet-history.js`, in `refresh-all.js` (see FRESHNESS below) —
UNLIKE mint_rankings' old staleness caveat, this table was designed hourly-fresh from
day one, no transition period.

SCHEMA — table `sweet_transaction_history`, PRIMARY KEY (tx_hash, token_uri)
  tx_hash               TEXT    -- parsed from explorer_url, NOT returned as its own
                                    field by Sweet's API
  token_uri             TEXT    -- the SPECIFIC EDITION's token_uri (series URL + a long
                                    numeric suffix) — CORRECTED 2026-09-02, this note
                                    used to wrongly call it opaque: it IS the exact same
                                    value as cards.token_uri / packs.token_uri for that
                                    specific card/pack. Verified directly: 754,331 of
                                    754,573 rows (99.97%) exact-match one or the other
                                    (423,987 -> cards, 330,344 -> packs). This is the
                                    RIGHT way to resolve a transaction to a highlight
                                    name/player/team/set — NOT series_id+edition (series_id
                                    is shared across every moment in a collapsed set, see
                                    the collections/moments section above, so series_id+
                                    edition alone returns one row PER SHARED MOMENT, e.g.
                                    32 different players for one Ice Nation edition
                                    number — genuinely ambiguous, verified live). The
                                    ~0.03% that don't resolve are a real, small, known gap
                                    (one repeated token_uri observed, likely a dead/edge-
                                    case moment not currently in `cards` — not investigated
                                    further, treat a LEFT JOIN miss as "highlight unknown"
                                    for display, don't treat it as a bug to chase)
  transaction_type      TEXT    -- 'purchase' | 'trade' | 'gift' | 'pack_open' | 'promo'
                                    | 'transfer' — exact values, verified against real
                                    rows of each (see GOTCHA below for what each really
                                    means in from/to terms)
  transaction_datetime  TEXT    -- ISO-8601-like but NAIVE (no timezone suffix, e.g.
                                    "2026-09-02T13:21:19") — assume UTC. String-sortable
                                    (ORDER BY works correctly as text) but don't display
                                    it as if it already has a timezone.
  series_id             TEXT    -- joins to moments.series_id / pack_moments.series_id
  edition               INTEGER -- the edition number this transaction was for — joins
                                    to cards.edition_number / packs equivalent alongside
                                    series_id
  amount                REAL    -- ONLY populated on 'purchase' rows (secondary-market
                                    sale price); NULL on every other type
  currency              TEXT    -- ONLY populated alongside amount, observed value
                                    "usd" so far
  from_username         TEXT    -- see GOTCHA below — not always a real username
  to_username           TEXT    -- see GOTCHA below — not always a real username
  explorer_url          TEXT    -- https://polygonscan.com/tx/{tx_hash}, safe to link
                                    directly
  scraped_at            TEXT    -- when OUR pipeline pulled this row, not when the
                                    transaction happened — use transaction_datetime for
                                    display/sort, scraped_at only for pipeline debugging

GOTCHA — from_username/to_username ARE NOT ALWAYS RESOLVED USERNAMES, VERIFIED 2026-09-02
Real per-type semantics, confirmed against one sample row of each type:
  purchase:  from_username = seller, to_username = buyer, amount/currency populated
             (this is a peer-to-peer secondary-market sale, not a primary Sweet-store
             purchase — from_username is a real seller, not a system/store account)
  trade:     both populated, no amount — direct wallet-to-wallet trade
  gift:      both populated, no amount
  pack_open: from_username == to_username == the SAME wallet (the opener) for 97% of
             rows (155,926/160,750) — opening a pack is modeled as a self-transfer. Use
             to_username (or from_username, identical) for a "most packs opened"
             leaderboard. The other 3% (4,824/160,750, verified 2026-09-02) are ALL
             from_username = "NHL" (the platform/brand account, same one seen on some
             'promo' rows) with to_username = the recipient — a promotional/granted pack
             the platform itself issued and opened directly to a wallet, not the
             collector opening one they acquired themselves. Both cases still correctly
             attribute the resulting cards' ownership via to_username; the "NHL" ones
             just shouldn't be miscounted as the recipient having "chosen" to open a
             pack if that distinction ever matters for a feature.
  promo:     from_username can be a literal brand string like "NHL", not a real user —
             exclude promo rows' from_username from any "top senders" leaderboard, it's
             not a collector.
  transfer:  from_username is a real username, but to_username is FREQUENTLY a raw 0x
             wallet address instead of a username (822/866 = 95% of all 'transfer' rows,
             819 of those an exact match to a KNOWN system_wallets entry — this type is
             mostly cards moving INTO a system wallet, e.g. crafting turn-ins, not
             regular user-to-user activity).
Broader finding, not just 'transfer': across the WHOLE table, 12,361 rows (~1.6%) have a
raw 0x-address string in from_username or to_username instead of a resolved username.
Only 819 of those 12,361 match a known system_wallets entry — the rest are NOT resolvable
via wallet_usernames either (checked directly, 0 matches), meaning Sweet's own API
returns the raw address for wallets that simply have no public username set. Before
using from_username/to_username as a display name or a leaderboard grouping key, check
it doesn't match a 0x-address shape (regex `^0x[0-9a-fA-F]{40}$` in Postgres: `to_username
~ '^0x[0-9a-fA-F]{40}$'`) and decide per-feature whether to exclude those rows, label them
"Unknown wallet", or show the truncated address — there's no username to fall back to for
most of them.
Note this table does NOT store wallet_address as its own column at all — only whichever
username/address string Sweet's API returned. If you need to go username -> wallet_address
(e.g. to link into an existing wallet profile page), join wallet_usernames on username;
that mapping is separate and NOT guaranteed to cover every value seen here (see above).

EXAMPLE QUERIES
- Sitewide recent activity feed, WITH the player/highlight name resolved (resolves open
  question #1 below) — join token_uri directly, NOT series_id (see the token_uri gotcha
  above for why series_id alone is ambiguous for shared-series sets):
    SELECT h.transaction_type, h.transaction_datetime, h.edition, h.amount, h.currency,
           h.from_username, h.to_username, h.explorer_url,
           c.player, c.team, c.rarity, c.set_name  -- NULL if it was a pack, use p.* instead
    FROM sweet_transaction_history h
    LEFT JOIN cards c ON c.token_uri = h.token_uri
    ORDER BY h.transaction_datetime DESC
    LIMIT 50
  For a feed that also covers pack transactions, LEFT JOIN packs p ON p.token_uri =
  h.token_uri too and COALESCE the display fields (pack_moments has pack_name/rarity,
  not player/team). A row where both joins miss (the ~0.03% gap noted above) should just
  show "Unknown item," not be dropped or treated as an error.
- Per-highlight activity tab for ONE specific card design (the thing nhlbreakaway.com's
  own series page shows, e.g. nhlbreakaway.com/series/X1OvMnqm) — resolve the target
  moment's OWN token_uris first (a shared series_id means you can't just filter
  `WHERE series_id = ?`, that would pull in every other moment sharing it too):
    SELECT h.* FROM sweet_transaction_history h
    WHERE h.token_uri IN (SELECT token_uri FROM cards WHERE moment_uuid = $1)
    ORDER BY h.transaction_datetime DESC
    LIMIT 100
  (For a whole SET's combined activity feed instead of one highlight, filtering by
  series_id directly is fine and intentional — that's the "everything sharing this
  series" scope, e.g. all 32 Ice Nation players' combined history.)
- "Who's opened the most packs" leaderboard:
    SELECT to_username, COUNT(*) AS packs_opened
    FROM sweet_transaction_history
    WHERE transaction_type = 'pack_open' AND to_username !~ '^0x[0-9a-fA-F]{40}$'
    GROUP BY to_username
    ORDER BY packs_opened DESC
    LIMIT 25
- "Most trades" leaderboard (a wallet can appear as either side of a trade):
    SELECT username, COUNT(*) AS trades FROM (
      SELECT from_username AS username FROM sweet_transaction_history WHERE transaction_type = 'trade'
      UNION ALL
      SELECT to_username AS username FROM sweet_transaction_history WHERE transaction_type = 'trade'
    ) x
    WHERE username !~ '^0x[0-9a-fA-F]{40}$'
    GROUP BY username
    ORDER BY trades DESC
    LIMIT 25
- "Top spenders" / "Top sellers" (secondary-market purchases only, real USD amounts) —
  there is NO separate 'sale' transaction_type; a `purchase` row already IS both sides
  of the same event at once (from_username = seller, to_username = buyer, amount = sale
  price) — a wallet's purchase is logically the other wallet's sale, same row, just
  group by the other column:
    -- spenders (money out)
    SELECT to_username AS buyer, COUNT(*) AS purchases, SUM(amount) AS total_spent_usd
    FROM sweet_transaction_history
    WHERE transaction_type = 'purchase' AND currency = 'usd'
    GROUP BY to_username
    ORDER BY total_spent_usd DESC
    LIMIT 25
    -- sellers (money in) — identical query, from_username instead of to_username
    SELECT from_username AS seller, COUNT(*) AS sales, SUM(amount) AS total_earned_usd
    FROM sweet_transaction_history
    WHERE transaction_type = 'purchase' AND currency = 'usd'
    GROUP BY from_username
    ORDER BY total_earned_usd DESC
    LIMIT 25
- Per-wallet activity page (this is the "wallet activity history" feature nhlba.com and
  thefifthlinecode.onrender.com show, e.g. nhlba.com/accounts/activity/{address}) — go
  address -> username via wallet_usernames first, since this table has no address column,
  then join token_uri for the highlight name the same way as the activity feed above:
    SELECT h.*, c.player, c.team, c.set_name
    FROM sweet_transaction_history h
    LEFT JOIN cards c ON c.token_uri = h.token_uri
    WHERE h.from_username = $1 OR h.to_username = $1
    ORDER BY h.transaction_datetime DESC
    LIMIT 100
  ($1 = the username resolved from the looked-up wallet_address.)

KNOWN LIMITATION — INCOMPLETE ON HIGH-VOLUME SERIES, VERIFIED 2026-09-02, ACCEPTED AS-IS
The bare-series aggregate endpoint used for the whole backfill (`/distribution/history/
{bare series URL}`) does NOT return 100% of that series' real transactions — verified
directly against Sweet's OWN per-edition endpoint (`/distribution/history/{that specific
card's own token_uri}`), which has more complete data than the aggregate view for the
same series. Found via a real user report: a trade showed only its "sent" leg in our
table (Kent Johnson -> gbeyond) but not the "received" leg (Cole Caufield <- gbeyond) —
confirmed the received leg is a real, separate on-chain transaction (different tx_hash
entirely, same timestamp) that Sweet's per-edition endpoint returns but the bare-series
endpoint never did, across a FULL clean pagination of that series (35,499 rows, ended
naturally on a sub-500 last page, no errors/truncation on our end).
Quantified via live spot-checks (compared this table's stored tx_hash set per card
against a fresh live call to that same card's per-edition endpoint):
  - Random sample across the whole catalog (30 cards, mixed series): 0 gaps found.
  - Targeted sample of ONE specific high-volume series, BjqGw7qp/"Base" (20 cards): 2/20
    cards (10%) had a missing transaction, one of them missing 2 of 3 real trades.
  - The high-volume/heavily-shared series (>10,000 cards each, 16 of them: ebWVvd1G,
    QqBmkGRA, gb04X2bA, BjqGw7qp, AqkW0kq6, QRvZmARw, NbnnQzbW, LRgw7JR6, zqlMjN1N,
    rb2kx7Rd, V1P88Z1d, yRzEN8bP, r1JoM3bv, j1ZJjx1K, 5RNBByRM, YqrMgPRJ) together account
    for ~961,000 of the ~1.14M total cards (~84% of the whole catalog) — because heavy
    sharing is what MAKES a series high-volume, "the big series" effectively means "most
    of the catalog," not a small corner of it.
DECISION, 2026-09-02: accepted as a known limitation, NOT worth fixing via a full re-
scrape. A complete fix would mean querying the PER-EDITION endpoint once per individual
card instead of once per series — for the ~961K affected cards, at the same ~400ms/
request politeness pace used everywhere else in this pipeline, that's roughly 4-5 DAYS
of continuous fetching, a completely different scale of effort than the 281-request
series-level backfill this feature was actually built on. Given the feature's real use
case (fun leaderboards, activity feeds — not financial reconciliation), an estimated
~90%-complete picture on high-volume series was judged good enough. If you build
anything that displays trade/activity history, don't present it as a guaranteed-complete
record — a wallet's real activity may include occasional gaps, especially on Base/heavily-
shared sets, and that's expected, not a bug to chase.

ALSO CONSIDERED AND DECLINED, SAME DAY: an Alchemy-based hybrid fix (full on-chain
`alchemy_getAssetTransfers` per contract — already used for burn detection in
`detect-burns.js` — dedup by tx_hash against this table, add whatever Alchemy sees that
Sweet doesn't). Investigated seriously, not just theoretical: verified the missing
Cole Caufield transaction directly on-chain via Alchemy (confirmed `tokenId` maps exactly
to `sequence_number`, `to` address matched the real wallet, timestamp matched), and
measured real scale (one 75K-card contract alone had 242,421 total on-chain transfers —
extrapolated to ~4-4.5M across the whole catalog, feasible in ~30-45 min of fetching, NOT
a scale blocker on its own). Declined anyway for two reasons the user raised directly:
(1) most of that volume (~1.3M) is MINT events, which would need to go somewhere other
than this table to avoid pushing Raff too close to its 2GB cap even after separating
mints from real gap-filling transfers; (2) an on-chain-only-recovered transfer has NO
way to distinguish gift vs. trade vs. private purchase — that categorization is Sweet's
own off-chain business logic, not present in a raw Transfer event, so any row rescued
this way would need an honest 'unknown category' label rather than a guessed one. Given
the added complexity for a fun-stats feature (not financial reconciliation), the user's
call was to stop here and keep the existing Sweet-only pipeline as the final state — if
this idea resurfaces later, this paragraph is the prior art, not a reason to assume it
wasn't considered.

STORAGE / SCALE NOTE
445MB with its 4 indexes (series_id, transaction_type, to_username, from_username) for
754K rows on Raff — pushed there in full (not pre-compiled into leaderboards), the
user's explicit call: Raff has no per-row-write billing (unlike the abandoned Turso, see
[[project-turso-infrastructure]]) and 2GB of free-tier storage headroom, so there's no

FRESHNESS
`sync-sweet-history.js` runs every hour as part of `refresh-all.js`, right before
`build-mint-rankings.js`/`sync-to-raff.js`. It does NOT re-walk full history each time —
per series, it checks only the newest page and stops as soon as a page is fully
duplicate, so a routine run only adds genuinely new transactions (verified live: found
73 new rows on its first post-backfill run, 2 more on an immediate re-run, 12 more in a
full `refresh-all.js` dry run — each consistent with real ongoing trading activity, not
a bug). New series (e.g. a newly-discovered pack template) are picked up automatically
next run since it queries `moments`/`pack_moments` for the current distinct series_id
list fresh every time, not a fixed one baked in at backfill time.

FLOOR PRICES — NEW 2026-09-03, BUILT AND POPULATED, HOURLY FROM NOW ON
Built for a "display the value of a wallet" feature (2-3000+ assets per wallet in the
worst case) — live-fetching Sweet per asset at view time was ruled out as too costly/
impolite at that scale, so this is a stored hourly snapshot instead. Storage only: no
aggregation/display logic was built on top of this on the NHL Breakaway side — that's
explicitly being built here in PopInStock3.0, not handed over pre-computed.

WHAT IT IS
The cheapest currently-open fixed-price marketplace listing for every real moment
(highlight template) AND every pack design, from Sweet's public
`/catalog/listing/moments` and `/catalog/listing/packs` endpoints (same query shape,
different path + uuid meaning — the packs endpoint was undocumented anywhere until found
2026-09-03 by network-inspecting nhlbreakaway.com/marketplace?assetType=pack). Both are
wrapped in lib/sweetClient.js as getOpenListings(momentUuid)/getOpenPackListings(packUuid).
Built by scripts/build-floor-prices.js: one call per asset (~2,150 total: 1,962 moments +
185 packs), limit=100 per call (no scroll loop needed — real per-asset open-listing counts
observed so far stay well under 100), floor = a real MIN over all returned listings'
current_offers[0].price_usd (not a blind trust of the API's own sort=price.asc). Verified
live against the marketplace UI itself: "Series 3 Grand Finale Pack" — total=27 listings,
price_usd=5.80 — matched the page's own "27 Available / $5.80 USD" exactly.

SCHEMA — table `floor_prices`, PRIMARY KEY (asset_uuid, asset_type)
  asset_uuid       TEXT    -- moments.moment_uuid OR pack_moments.pack_uuid, per asset_type
  asset_type       TEXT    -- 'moment' | 'pack' — always filter/join on this, asset_uuid
                               alone is not guaranteed globally unique across both types
  price_usd        REAL    -- NULL if this asset currently has ZERO open listings — a real,
                               common state (see GOTCHA below), NOT an error and NOT $0.
                               Roughly 60% of moments/packs have a live floor at any given
                               time (1,355/2,147 on the initial backfill) — don't assume
                               every held asset will price.
  listings_count   INTEGER -- how many open listings this floor was computed over (0 when
                               price_usd is NULL)
  listing_id       TEXT    -- the cheapest listing's own id — https://sweet.io/listings/
                               {listing_id} is a real, clickable link to it (same link shape
                               dev-server's existing fetchSweetListings already uses)
  updated_at       TEXT    -- when this row was last (re)computed — the whole table shares
                               essentially one timestamp per refresh-all run, not a per-row
                               freshness signal

JOINING TO A WALLET'S HOLDINGS
  Highlights: cards.moment_uuid = floor_prices.asset_uuid AND floor_prices.asset_type =
    'moment'. Floor price is per TEMPLATE — a plain JOIN (one floor_prices row matched to
    every owned `cards` row of that moment) already gives price × quantity-held correctly
    when summed, no separate multiplication needed, since a wallet holding 3 copies of one
    moment produces 3 joined rows each carrying that same price.
  Packs: packs.pack_uuid = floor_prices.asset_uuid AND floor_prices.asset_type = 'pack'
    (packs table, not pack_moments — pack_moments is the design catalog, packs is who
    owns which pack editions, same cards/moments split). Filter packs.burned = 0 for
    "currently held", same convention as cards.
  A LEFT JOIN (not INNER) is the right choice for either — an owned asset with no floor
    row match, or a NULL price_usd, means "no current listings to price this against",
    which the UI needs to represent explicitly rather than silently dropping the asset or
    treating it as worth $0.

GOTCHA — SINGLE-LISTING OUTLIER PRICES, FOUND 2026-09-03, NOT FILTERED AT STORAGE
~22 of the 1,257 currently-priced moments (concentrated entirely in the lowest-liquidity
tiers — Signature Rares/Heroics/Limiteds/Epics, 1-of-1 "Ice Vault" Mythics, "Legendary"
tier) have a single open listing at a wildly aspirational/troll price with no competing
seller to undercut it — e.g. Nick Suzuki "Signature Heroics" at $999,998, Sidney Crosby
"Signature Rares" at $878,787.90, Mario Lemieux at $166,000. These are genuinely real,
correctly-computed floors (the true MIN of that asset's only listing) — not a pipeline
bug, so price_usd was deliberately left as-is rather than filtered/capped in storage. The
shared tell across all of them is listings_count = 1 combined with a price far outside
that collection's normal range; an earlier design draft added a computed is_outlier flag
to this table for a value-aggregation consumer to key off, but that was reverted 2026-09-03
at the user's explicit call ("just store the floor prices, I'll manage display") — if you
build a wallet-value feature on this table, decide your own outlier-handling rule (or none)
rather than assuming raw SUM(price_usd) is a safe/meaningful headline number as-is.

PACK OPENING HISTORY — NEW 2026-09-04, BUILT, ONE DROP FULLY BACKFILLED, HOURLY FROM NOW ON
Built for a "reproduce nhlba.com/packages/opened/117" page — per-pack-opening history (who
opened it, when, and which highlights came out), filterable by set/username/etc. This is
the piece Sweet's own API has NO endpoint for at all (not even close — nothing in
/distribution/history or /catalog ties a pack burn to the cards it produced). Resolved
entirely via Alchemy/Polygonscan, not Sweet.

WHAT IT IS AND HOW IT WORKS
Verified live 2026-09-04 against a real pack open before building anything: opening a pack
transfers N pre-existing card editions from the `pack_escrow` system_wallets entry
(0x610123c1f5e34974c63343c84973cd5603b08e7c — the same wallet already behind "In Packs"
elsewhere in this schema) to the opener, in the SAME on-chain transaction as the pack's own
burn. detect-burns.js (which already finds every pack burn) now also captures that
transaction's hash (`packs.burned_tx_hash`, free — Alchemy's alchemy_getAssetTransfers
always returned this, it just wasn't stored before). A new script,
scripts/resolve-pack-openings.js, fetches that transaction's FULL receipt
(eth_getTransactionReceipt — every log in it, not just the pack's own burn transfer) and
records every pack_escrow-to-opener Transfer it finds on a KNOWN CARD contract (via
`series_contracts`) as `cards.pulled_from_pack_token_uri`. No new tables — this rides on
the existing `cards`/`packs` tables (and their existing sync-to-raff.js config) rather than
a parallel schema.

NO NEW COLUMNS FOR NAME/RARITY/ETC ARE NEEDED — a pulled card's `cards` row already has
moment_uuid (plus already-denormalized player/team/set_name/rarity, same as every other
cards row) since it's the SAME cards table build-moments.js/reconcile-cards.js/
detect-burns.js already populate. Join to `moments` on moment_uuid for the canonical/
fuller version (badges, jersey_number, etc.) exactly like every other feature in this doc.

SCHEMA — 4 new columns, no new tables
  packs.burned_tx_hash          TEXT  -- the opening transaction's hash. Polygonscan link
                                          is NOT stored separately (redundant, pure prefix)
                                          — build it as https://polygonscan.com/tx/{hash}
  packs.pulls_resolved_at       TEXT  -- set once resolve-pack-openings.js has processed
                                          this pack's burn tx (even a genuine 0-pull result
                                          sets this — it's a "we looked" marker so nothing
                                          gets retried forever, not a "found something" one).
                                          NULL = not opened yet, OR opened but not yet
                                          processed (burned_tx_hash also NULL in that case
                                          until detect-burns.js's next run catches it)
  cards.burned_tx_hash          TEXT  -- same idea, captured for cards' own burns too
                                          (crafting etc.) — not used by this feature, added
                                          for free since the burn-detection code path is
                                          shared between cards and packs
  cards.pulled_from_pack_token_uri TEXT -- set to packs.token_uri when this specific card
                                          edition was identified as one of the highlights a
                                          specific pack produced. NULL = unresolved/unknown
                                          provenance, NOT "wasn't from a pack" — plenty of
                                          real cards will never get backfilled (see BACKFILL
                                          SCOPE below)

HOW TO BUILD THE PAGE — every query below run and verified live against real Raff data
2026-09-04 (not theoretical — actual rows/counts shown are real, from the 8R5xYdbD drop).

1. PAGINATED LISTING (the main page — one row per opened pack, highlights inline, ONE query,
no N+1): json_agg pulls each pack's highlights into the same query as the header + total
count, same "COUNT(*) OVER() so pagination needs no second round-trip" convention this
dev-server already uses everywhere else (see SETS_SQL/handleWalletCards etc). Verified: for
pack_uuid b572cf35000000009ff1000000000000, page 1 returned total_count=1510 and (among
others) edition #2287 opened by "uncgpa" 2026-09-04T13:42:51Z with exactly the 4 highlights
this doc's earlier version already listed by hand.
  SELECT p.token_uri, p.pack_uuid, p.pack_name, p.series_label, p.rarity, p.edition_number,
         p.burned_by_wallet, wu.username AS opener_username, p.burned_at, p.burned_tx_hash,
         -- build the polygonscan link client-side: 'https://polygonscan.com/tx/' || burned_tx_hash
         COUNT(*) OVER() AS total_count,
         json_agg(json_build_object(
           'moment_uuid', c.moment_uuid, 'player', c.player, 'team', c.team,
           'set_name', c.set_name, 'rarity', c.rarity, 'edition_number', c.edition_number
         ) ORDER BY c.token_uri) AS highlights
  FROM packs p
  LEFT JOIN wallet_usernames wu ON LOWER(wu.wallet_address) = LOWER(p.burned_by_wallet)
  JOIN cards c ON c.pulled_from_pack_token_uri = p.token_uri
  WHERE p.pulls_resolved_at IS NOT NULL
    -- optional filters, all tested: AND p.pack_uuid = $n (one specific drop/pack design)
    -- AND p.series_label = $n / AND p.rarity = $n (broader set filter)
    -- AND wu.username = $n (by opener username) / AND LOWER(p.burned_by_wallet) = LOWER($n) (by raw wallet)
  GROUP BY p.token_uri, p.pack_uuid, p.pack_name, p.series_label, p.rarity, p.edition_number,
           p.burned_by_wallet, wu.username, p.burned_at, p.burned_tx_hash
  ORDER BY p.burned_at DESC
  LIMIT $limit OFFSET $offset
Note the JOIN (not LEFT JOIN) on cards — deliberate, a resolved pack with genuinely 0 pulls
has never been observed (0/1510 so far) so this can't silently hide a pack; if that ever
does happen it'll correctly vanish from this listing rather than show an empty highlights
array, which is arguably the more surprising failure mode — switch to LEFT JOIN + COALESCE
if you'd rather it show up with an empty pull list instead.

2. FILTER BY A SPECIFIC HIGHLIGHT ("which packs produced this card") — reverse of the above,
useful for a moment's own page ("pulled from these packs"):
  SELECT p.token_uri, p.pack_name, p.burned_at, p.burned_by_wallet, wu.username, c.edition_number
  FROM cards c
  JOIN packs p ON p.token_uri = c.pulled_from_pack_token_uri
  LEFT JOIN wallet_usernames wu ON LOWER(wu.wallet_address) = LOWER(p.burned_by_wallet)
  WHERE c.moment_uuid = $1
  ORDER BY p.burned_at DESC

3. FILTER-DROPDOWN SOURCES (same "distinct values from what's actually resolved" convention
as handleHighlightsFilters/handleWalletActivityFilters elsewhere in this file):
  SELECT DISTINCT p.pack_name, p.pack_uuid FROM packs p WHERE p.pulls_resolved_at IS NOT NULL ORDER BY p.pack_name
  SELECT DISTINCT p.series_label FROM packs p WHERE p.pulls_resolved_at IS NOT NULL ORDER BY p.series_label
  SELECT DISTINCT p.rarity FROM packs p WHERE p.pulls_resolved_at IS NOT NULL

4. "PULL ODDS SO FAR" (empirical, per pack design) — verified for the 8R5xYdbD drop: 152
distinct highlights observed across 1,510 packs/6,040 total pulls so far, top of the list all
Ice Nation (Series 3) Fandom cards at ~121-129 pulls each:
  SELECT c.moment_uuid, c.player, c.set_name, c.rarity, COUNT(*) AS times_pulled,
         COUNT(*)::float / (SELECT COUNT(*) FROM cards c2 JOIN packs p2 ON p2.token_uri = c2.pulled_from_pack_token_uri WHERE p2.pack_uuid = $1) AS observed_share
  FROM cards c
  JOIN packs p ON p.token_uri = c.pulled_from_pack_token_uri
  WHERE p.pack_uuid = $1
  GROUP BY c.moment_uuid, c.player, c.set_name, c.rarity
  ORDER BY times_pulled DESC

observed-frequency estimate above): NHL Breakaway's own drop pages
(https://nhlbreakaway.com/drop/{series_id}) link a "Highlights List" — a published Google

TABLE `pack_highlight_pools`, PRIMARY KEY (pack_uuid, moment_uuid) — deliberately minimal,
NOTHING duplicated that's already on `moments` (name/rarity/team/etc — join moment_uuid
there for all of that, exactly like every other table in this doc):
  pack_uuid          TEXT     -- which pack design (packs.pack_uuid / pack_moments.pack_uuid)
  moment_uuid         TEXT    -- which highlight (moments.moment_uuid)
  approx_avail        INTEGER -- sourced quantity for THIS highlight individually. 0 when
                                  approx_avail_set is used instead (see below) — never both
  approx_avail_set     INTEGER -- sourced quantity SHARED across every highlight in this
                                  one's group/tier in the source sheet (e.g. one drop's
                                  Legendary tier: "1 highlight total" across 5 players means
                                  1 pull total shared between all 5, not 1 each). 0 when
                                  approx_avail is used instead
  updated_at           TEXT

REMAINING-PULLS FORMULA, verified live against real data on both imported drops:
  -- per-highlight case (Nick Suzuki, Series 3 Grand Finale / 8R5xYdbD drop):
  -- sheet says 54 available, pack-opening history shows 37 pulled so far -> 17 remain
  SELECT php.approx_avail - COUNT(c.token_uri) AS remaining
  FROM pack_highlight_pools php
  JOIN moments m ON m.moment_uuid = php.moment_uuid
  LEFT JOIN packs p ON p.pack_uuid = php.pack_uuid
  LEFT JOIN cards c ON c.pulled_from_pack_token_uri = p.token_uri AND c.moment_uuid = php.moment_uuid
  WHERE php.pack_uuid = $1 AND php.moment_uuid = $2 AND php.approx_avail > 0
  GROUP BY php.approx_avail
  -- shared-pool case (Playoff Bound 2026 / 61p6QVRP drop's "The Greatest Achievements"
  -- Legendary tier, 5 players): sheet says 1 shared, 1 already pulled (any of the 5) -> 0
  -- remain for ALL FIVE, not "1 remaining" on the 4 not-yet-pulled ones. Group by
  -- (pack_uuid, m.set_name) — a shared-pool group is always one full section/tier of the
  -- source sheet, and set_name is the reliable way to identify that group (two DIFFERENT
  -- shared-pool groups on the same pack could coincidentally have the same approx_avail_set
  -- number, so don't group on that alone). Tested live, returns exactly {set_name:
  -- "The Greatest Achievements", pool_size: 1, pulled_so_far: 1, remaining_for_whole_group: 0}:
  WITH group_moments AS (
    SELECT php.pack_uuid, m.set_name, php.moment_uuid, php.approx_avail_set
    FROM pack_highlight_pools php
    JOIN moments m ON m.moment_uuid = php.moment_uuid
    WHERE php.pack_uuid = $1 AND php.approx_avail_set > 0
  )
  SELECT gm.set_name, MAX(gm.approx_avail_set) AS pool_size,
         COUNT(c.token_uri) AS pulled_so_far,
         MAX(gm.approx_avail_set) - COUNT(c.token_uri) AS remaining_for_whole_group
  FROM group_moments gm
  JOIN packs p ON p.pack_uuid = gm.pack_uuid
  LEFT JOIN cards c ON c.pulled_from_pack_token_uri = p.token_uri AND c.moment_uuid = gm.moment_uuid
  GROUP BY gm.set_name

PAUSE-THE-SCHEDULER TECHNIQUE, ADDED 2026-09-05 PER DIRECT USER INSTRUCTION — for a drop
whose resolve step won't comfortably fit the remaining window before the next scheduled
refresh-all, don't skip the cycle: temporarily disable the Windows scheduled task itself for
the duration of the import, then re-enable it.
  `Disable-ScheduledTask -TaskName "NHL Breakaway Refresh"` before starting Alchemy calls,
  `Enable-ScheduledTask -TaskName "NHL Breakaway Refresh"` once sync-to-raff.js has run and
  the drop is verified. Confirmed side effect: a disabled task's missed trigger is NOT made
  up when re-enabled (a simple hourly recurrence just skips the slot that fell inside the
  disabled window) — e.g. disabling from ~12:33AM to ~12:47AM skipped the 12:46:55AM run
  entirely, jumping straight to 1:46:55AM, a ~2hr gap that one time instead of the usual
  ~1hr. This is an accepted, explicitly-approved tradeoff, not a bug to fix — just don't
  forget the re-enable step, and don't leave it disabled longer than the one drop's import
  actually needs.

SHARED MULTI-TAB WORKBOOKS — THE REAL EXPLANATION, CORRECTED 2026-09-05 (supersedes an
earlier wrong theory in this doc's history). What first looked like two separate problems —
"the same URL served different drops' content at different times" (drop #10) and "some
'Debut LE' packs have no dedicated sheet, just page-published slot percentages" (drops
#12/#13) — turned out to be ONE thing, found by the user directly inspecting the actual
spreadsheet (not just its CSV export): NHL Breakaway does NOT publish one workbook per pack.
It publishes one workbook per RELEASE DATE (e.g. "NHL Breakaway - Nov 11 Drop Highlights",
"NHL Breakaway - Oct 9 Drop Highlights"), with ONE TAB PER PACK that launched that day. A
drop's "Highlights List" link always points at that shared workbook's PUBLISHED (default)
URL — which has no way to select a tab unless a `gid=` is appended. Fetching `/pub?
output=csv` with no gid silently returns whichever tab is gid=0 (first/leftmost) — a
DIFFERENT pack's data, not an error, which is exactly why it looked like "wrong content"
rather than "missing content."
THE FIX: `import-pack-highlight-pool.js`'s `toCsvUrl()` now extracts a `gid` from the input
URL (works whether it's `...#gid=123` — what you get copying a tab's URL out of the address
bar after clicking it — or `...?gid=123`) and forwards it to the CSV export call. To get the
CORRECT tab's URL for a drop whose default tab doesn't match: open the drop's Highlights
List link in a browser, look at the tab bar at the bottom of the page, click the tab
matching that drop's own name, then copy the resulting address-bar URL (it'll have
`#gid=...` appended) — that's what to pass to the import script.

SYNC-TO-RAFF WATERMARK RACE — REAL BUG FOUND AND FIXED, 2026-09-05. `sync-to-raff.js`
advances each table's watermark to `syncStartedAt` (captured at THAT sync's own start)
unconditionally, regardless of whether every row up to that timestamp was actually captured.
`resolve-pack-openings.js` used to stamp EVERY row from one entire run (which can take 40+
minutes on a large drop) with a SINGLE timestamp captured once at the run's start. If a
sync-to-raff.js run executes WHILE a resolve-pack-openings.js run is still writing, the
sync's watermark can advance past that shared timestamp — and every row the still-running
resolve script writes AFTER that point (still stamped with the now-in-the-past shared value)
becomes PERMANENTLY invisible to every future incremental sync, since its scraped_at will
always be less than the already-advanced watermark. This actually happened: running
sync-to-raff.js for the drops #12/#13 fixes while drop #14's resolve-pack-openings.js was
still active in the background left ~978 of drop #14's 4,822 packs (and their ~2,900 linked
cards) permanently stuck — confirmed by comparing local vs Raff counts directly (resolved:
4,822 local vs 3,844 Raff; the packs ROWS all existed on Raff already from earlier scraping,
only the burned/pulls_resolved_at field UPDATEs were the ones lost).
FIXED at the root cause: `resolve-pack-openings.js` now captures a FRESH timestamp per pack
INSIDE its main loop, not one shared value for the whole run — a row's scraped_at now always
reflects roughly when it was actually written, so a concurrent sync can only ever miss the
still-in-flight tail, and that tail's later (still-fresh) timestamps get correctly picked up
by the very next sync. The run's own end-of-run sanity check (previously keyed off the shared
timestamp) now tracks its own processed-token_uri list in memory instead.
RECOVERED the already-stuck drop #14 rows with a new one-off, `scripts/fix-stale-sync-
timestamps.js <pack_uuid>` — bumps scraped_at to NOW for every packs/cards row tied to a
pack_uuid, forcing the next sync to pick them all up regardless of the current watermark
(safe/idempotent to run on already-correct rows too). Re-verified after: local/Raff now
match exactly (resolved: 4,822/4,822, burned: 4,822/4,822).
GENERAL LESSON: never run sync-to-raff.js while ANY Alchemy-heavy script from this workflow
(detect-burns.js, resolve-pack-openings.js, backfill-pack-burn-hashes.js) is still actively
running in the background — not just for the already-known "concurrent Alchemy requests
silently drop data" risk, but now also for this separate sync-watermark race. Wait for the
on-chain step to fully finish before running sync-to-raff.js, every time.

WHY THIS DATA IS LIKELY MORE ACCURATE THAN EXISTING FAN SITES
The NHL Breakaway project's cards/packs tables come from Alchemy on-chain data
(getOwnersForContract), not Sweet's own search index. Sweet's search index has a
documented, structural blind spot (misses first-claim/mint events, only sees transfers
between two already-named owners) that the *old* version of this very project used to
have before an Alchemy-based rebuild. Concrete evidence, not just theory: cross-checking
nhlba.com's own leaderboard today, its #2 real collector shows 7,431 total items; this
project's DB shows 9,717 for that exact wallet — which matches a number independently
verified against the official site's own ground-truth endpoint. If building a competing
or complementary site, this data pipeline is a genuine advantage worth leaning on.
